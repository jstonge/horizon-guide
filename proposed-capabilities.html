Why a capability list

A feature is the checklist page, the Ask tab or the draft_edit tool. A capability is a guarantee that holds across every feature, such as "we rate-limit each caller", "features open by role" or "the server reads production without exposing it". A new feature inherits the capabilities without extra code, and a refactor must not lose any of them.

Part A. The foundation

Most of the foundation belongs to the whole app, not only to the MCP server. Sign-in, roles, the party rule, the tiers, the spend caps and the history hold for a page in the browser as much as for an assistant. A few rows belong to the tools alone: one address, old names that still answer, the reply shape, lanes, and code that never sees a person.

A request's path

Every request, from a browser, a person's assistant or a service, passes the same five checkpoints. The families below follow them, then add what the system keeps.

3. Reaching production without exposing it

The tools answer from production's real data, and nothing travels further than its tier allows: not in a reply, not in a log, not in development.

The tier is the schema Every table's data class (Low or Moderate) is the schema it lives in, and each process connects as a role that holds grants on its tier only. The database refuses, not the code. roles mcp (Low only), web_app, pipeline; db/roles.sql; make tiers-check; decision 0003 in place⚑ tool-layer plan (parked: one connection)

Logs that cannot track people A log line names the caller's class (anonymous, token, app) and the tool, never the account, the token or any part of its digest, the arguments, or a database error's message, which can quote the query. tools/caller.ts, errorName; decision 0003's addendum; decision 0012, item 5 in place

Development never holds real people Outside production, the Moderate schemas hold synthetic personas only. Developers and agents work on real public data and fake people. decision 0006, item 5; seed personas; settings refuse production's database in place

4. Fair use and cost

No caller can take the box down or run up the bill, and each pays from their own budget.

CapabilityWhat it meansHow it holdsStatus
Rate limits per caller Each account has a bucket (120 units, refilled at 2 a second), and an expensive tool costs more than a cheap one. Each account also has a few in-flight slots, and a request body is capped at 4 MB. Callers behind IT's proxy cannot be told apart by IP, so limits key on the account, never the address. lib/server/rate-limit.ts, tool-runtime/limiter.ts, mcp/endpoint.ts; decision 0023, item 9 in place⚑ tool-layer plan: the in-app charge must survive
One budget, every door A tool call costs the same whether it came from the person's assistant or the platform's own Ask tab: both draw on the same account bucket. toolCaller({charge}) in tool-runtime/call.ts; decision 0023, item 9 in place⚑ tool-layer plan: not yet carried
Model spend is capped and ledgered Every paid model call is a row with its cost. The app has one daily cap, each account an allowance ($10 over a rolling window), and the Jev stand-in its own global daily cap. Over a cap, the call is refused before it is made. app.model_calls, model/ledger.ts, APP_MODEL_DAILY_MICROS, ACCOUNT_ALLOWANCE_MICROS; mcp.llm_spend; decision 0006, addendum 2026-10-15 in place

If assistants may, a rule says whose allowance it draws on and whether the reply is "started, read again later". decision 0020 ("no agent starts a draft"); the parity audit's candidates 1 and 8 proposed

5. Answers you can trust

Every answer says where it came from and how it was made, and a degraded answer says so.

CapabilityWhat it meansHow it holdsStatus
Every claim carries its source A rule comes with the document, its URL and the revision date UVM printed; an eligibility verdict with the funder's verbatim quote and "extracted by <model>, judged by rule"; a checklist item with the sentence it rests on. the tool contracts; the marts' dbt contracts in place
Degradation is never silent When a model behind a search is down and a fallback answers, the reply says which stage fell back. A page labels a degraded answer; a document tool says which half answered. lanes on every search and match; AGENTS.md in place
One reply shape everywhere Every tool answers {status, message, ...}: ok, truncated, not_found or refused, with a sentence saying what to do next. An assistant learns the shape once. lib/tools/envelope.ts; decision 0022, item 7 in place

Part B. Features built on the foundation

A feature is a page, usually with a model behind it. It inherits all of part A and adds three things of its own: what the model is told, which tools it may call, and how much one use may cost. Each model feature is a named surface with its own addendum to decision 0006, and every model call it makes is a row in app.model_calls under that name.

11. What a new feature inherits and declares

The two lists below are the recipe for the next feature, such as a third Ask tab.

It inherits

  • sign-in, roles and the party rule
  • access to each tier through that tier's role
  • the account's rate bucket, the daily cap and the allowance
  • a ledger row per model call
  • the tools, with their sources, their lanes and one reply shape
  • history events for anything it changes

It declares

  • a surface name and its addendum to decision 0006
  • its tools, by name from the one registry, and the scope the page fixes
  • its cost ceiling, with the arithmetic
  • what it stores, which by default is the ledger row alone
  • its benchmark, if it drafts, ranks or judges

What the owner would rule on

The proposed rows and the open questions behind the partial ones, in one place. Each is its own decision, and this page decides none of them.

  1. UVM's policies in the Ask tabs (section 9). Whether both tabs get uvm_requirements_search and uvm_requirements_read, with a new cost ceiling, and which audience a tab reads as.
  2. Assistants that start model runs (family 4): whether they may, and whose allowance pays. Today decision 0020 says no.
  3. Assistants that run a proposal end to end (family 7): which write tools, in what order. The parity audit ranks proposals_create, proposals_read and checklist_update first.
  4. Discoverability (family 6): a way to list funder guides, before deciding whether guides become their own tool family.
  5. Structured replies (family 5): whether the advertised schema is loose (adding a field stays free) or strict.
  6. Which audience a signed-in assistant is (family 3): it must not see staff-only text, but does see eligibility verdicts. This is the one tier choice inside the tool-layer plan.
  7. Parked, each later and alone: one database connection for the app instead of two (it would move the "database refuses" guarantee for services into code), and one token kind for people and machines.
