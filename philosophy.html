Tools, skills and evals first

How horizon is built, in what order, and why that order pays off over time, compared with the Codec prototype, which builds the same product one feature at a time.

1. Two ways to build the same product

Both projects want the same thing for UVM. A researcher finds funding and prepares a proposal, and SPA and research development staff help. The projects differ in where they start.

Feature first starts from a page. A mockup shows what a person should see, and the team builds the feature to match it, writing the data access, the prompt and the model call for that page. A feature is done when its page works.

Tools, skills and evals first starts from the record. The data comes first, then tools that answer questions over it, then the method for using the tools, then a way to measure whether the answers are good. A page comes last and calls the same tools anyone else would. A feature is done when its tools pass their tests and its model's work passes its benchmark.

Neither is wrong at every stage. Feature first is how a prototype gets its first users. This page asks which one still works after a year of changes.

2. horizon's order

  1. The data. There is one record, kept whole. Every source lands in the warehouse with its history, and where the data lives decides who may see it, not each page. Everything above reads from it (Data sources).
  2. Tools over it. Each question worth answering becomes a tool with a stated input and a stated reply, and the reply says which models produced it and which fell back. The app and a person's own assistant call the same tools, so each question has one answer, wherever someone asks it (Tools, skills, MCP).
  3. The method for using them. We write down once how to get a good answer out of the tools and how far to trust it, as a skill or a workflow, and the app and outside assistants both use it. The rules for quoting UVM's requirements, with their dates and sources, are one skill that the app's chat and Claude Code both read.
  4. Measurement. A benchmark of keyed answers judges a model's work. A change to a prompt, a model or a lane runs on its benchmark before it ships, and we cite a number with the run that produced it (Evaluation).
  5. The product. The app comes last and calls the tools. It adds what only a page can add: forms, review, and the conversation between a researcher and the people who help them.

3. The Codec prototype

Codec is a web portal organised as named agents, one for each area of the university's work, with grants first. Its team builds features one at a time from a design mockup that the people who will use them have reviewed.

The approach has strengths. It shows a whole lifecycle quickly, from a profile to a submitted proposal. It runs without a model key, because a local fallback answers in the model's place, which makes demos easy. It weighs matches against UVM's strategic priorities, and it keeps cost down by choosing a model for each job.

Each feature calls the model from its own code, with a prompt an admin can change in the console. Tests check the code around each call, and nothing measures whether the answers are good.

5. Why the order compounds

We pay for each layer once, and everything above it uses it. Three changes in horizon show this.

A fix reaches every caller at once

One of the documents tools sent more than an assistant needed. A single change trimmed it (!227), and the app and every outside assistant got the smaller reply together. In a feature-first build, each page would have carried its own copy to fix.

A benchmark stops a change before anyone sees it

Someone tried a new prompt for the checklist drafter. On its benchmark it found fewer of the sections a call requires, so it did not ship (!80). An admin editing it live would have sent it to every proposal, and nothing would have shown that the drafts got worse.

One authority for a number

A budget's arithmetic lives in one tool that looks up the rates itself. Every caller gets the same totals, and no model copies a rate from one answer into the next.

In all three, every layer above reuses the work done in a layer. In a feature-first build, only the page it was done for reuses it.

6. What it costs

  • A feature shows later. A page waits for its tools, and a model's job waits for a way to measure it. A prototype shows a whole lifecycle sooner.
  • More process. A decision comes before the code, checks run before every change, and a benchmark runs before a prompt change.
  • Harder to start. A newcomer meets the warehouse and the tools before the app. These pages exist to shorten that.
  • No answer without the model. horizon says when a model is down instead of answering in its place, so a demo without a key shows less.

Our assumption is that we pay these costs once per layer, while a feature-first build pays them again with every feature and every prompt edit.

7. What horizon takes from Codec

  • Its budget engine, ported and corrected, as horizon's one budget tool.
  • Its mockups, as a check that a page serves the person it is for. Tools can be right and still answer questions nobody asks.
  • Its strategic priorities. Should matching weigh them, and how would a benchmark measure that?
  • Its developers already call horizon's tools while they build, so one tool already serves both projects.

Open questions

  • Should horizon offer a labelled mode without a model key for demos and onboarding, or keep saying when a model is down?
  • Which Codec features would a tools-first build expose as tools first, so that both projects could call them?
  • Should UVM's strategic priorities enter matching, and how would the benchmark key them?
