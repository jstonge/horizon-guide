Drafts in Teams, read and written by agents

A proposal's checklist carried into its drafts, so that agents (the platform's and a person's own) can find, read and, in Markdown, write each checklist item's section.

Built 2026-10-26 on two branches, merged the same day: lane/drafts-read (sections 4–5's reading) and lane/drafts-write (Markdown and writing, off unless AGENT_DRAFT_WRITES=1); both ruled by the owner on 2026-10-27, writes on in production and judged in use (decision 0006's two addenda of 2026-10-26). Designed on branch proto/markdown-drafts (its prototype, never merged) (prototype and findings: findings/2026-10-25-markdown-drafts), reviewed by two advisor sessions (structure, then the change radius and its pruning). The rulings it needed are listed in section 8.

1. What it is for

Today a team's drafts sit in its Teams workspace as Word files, a folder per deliverable made from its row the first time it is needed (decision 0006, addendum 2026-10-26 on deliverables, 5), or one application file for the call's text fields. The platform can create an empty outline there and read a draft whole, but an agent cannot go to one checklist item's part of a draft, and nothing can write into one.

One feature, two ways in

The same tools serve the platform's own agent and a person's own agent on their subscription (Claude Code, Claude Desktop, any MCP client).

The checklist lives in the draft

Document, part, sub-part: each heading carries the id of the checklist item it answers, with what the call requires under it.

Navigate, never read whole

Outline, then a section by item, then a position inside it. A 20-page narrative (about 60,000 characters) never has to fit in one reply.

Write in place

Fill or extend an item's section without overwriting a co-author. Markdown only.

Stay in step

Items missing from the draft are inserted; a lost marker can be put back; the draft's own changes are reported.

Formats behind one interface

Word and Markdown now; LaTeX (Overleaf) later, without touching the tools.

People keep writing in Teams. Agents only ever write into a file the platform made; creating files stays on the platform's buttons.

2. The picture

3. Word or Markdown

A team chooses when it sets up the workspace. The format of a file is its extension; the workspace's choice is the team's consent to agent writes. A file is writable only when it is a .md, the workspace chose Markdown, and the file is one the platform made for the task and listed in the task's own folder, or, for a task with none, among the attempt folder's own top-level files, where the platform put it. There a read too sees only the task's own files (a provisioned link of the task, or named after it), never another task's outline or a person's upload beside it; and only a written deliverable (or a part of one) has a draft (decision 0006, addendum 2026-10-26 on deliverables, 2).

One application file, or a file per deliverable

Decision 0006's addendum 2026-10-26 on deliverables, 4. The default comes from the call: a deliverable submitted as a text field (Northeast SARE's sections) goes into one application file; an upload gets a file of its own; a form or a collected deliverable gets no draft. The team may override at set-up, beside the Word/Markdown choice: one application file or a file per deliverable, one choice per workspace. The application file is Word only: it is open all day, Word co-authors, and the hand test showed the Markdown web editor's autosave erasing an upload. The platform writes it once, at creation (Heading 1 per deliverable with its limit, parts beneath, a marker on every heading, the sponsor's instructions in the body, the review criteria as comments), and never again; agents read and check it. Every read is per deliverable: the deliverable's marked slice of the file and nothing else, so the draft check still never sends one deliverable's text with another's. A heading that lost its marker and matches an item's title at its level is read as that item, and said so. A page limit inside the shared file has no page count, as in Markdown. Agent writes stay with Markdown, a file per deliverable.

As built (B4b). The choice is offered wherever a workspace is set up, beside the Word/Markdown choice. The call's default is marked; keeping it stores no choice (null), so the call decides as its checklist is drafted. The file is made by the first "Create outline" or "Create document" on any deliverable that belongs in it, or on one of its parts, at the top of the attempt folder, named <proposal title> - Application.docx, with every deliverable that belongs in it at that moment, in the checklist's order; it is linked from each of them and from every part and sub-part, and later presses open it through that link. A deliverable that already holds a file of its own is never put in it. A deliverable added to the checklist after it was made gets a file of its own, in its own folder, even in this layout. A deliverable in the file gets no folder; "Open in Teams" on its row opens the file. The comments carry the format rules the checklist applies to the deliverable (applies_to); no other guidance is linked to a deliverable unless the data links it.

Word (.docx), the default

Agents read and check: outline, a section by item, a position inside it. People get everything Word gives: desktop and web, mature co-authoring, tracked changes, comments, reference managers, sponsors' templates, real page counts and the PDF the sponsor wants.

Markdown (.md)

Agents also write: fill a section, add to it, insert a missing one, put back a lost marker. People write in Microsoft's Markdown editor (web only, new in 2026). No page count, so the draft check cannot judge a page limit, and the sponsor's PDF is one render with a template from the sponsor's format rules.

GoalWordMarkdown
Read by sectionYes, through our XML reader, where the hidden bookmarks survivedYes; the marker is visible and repairable
Write in placeNo: the agent's text is not the file's (runs, styles, tracked changes)Yes: a splice in a text file
Insert a missing itemNo (reported only)Yes

From Markdown to the sponsor's PDF

The owner's direction (2026-10-26): a Markdown draft goes to the sponsor's PDF in one step, with pandoc and a template that applies the sponsor's formatting rules: font and size, margins, line spacing, page limit. The checklist already holds those rules as format items attached to their document (applies_to), so the template's settings can come from the checklist rather than from a person retyping them. The same render gives a real page count, so the draft check can judge a page limit on a .md again whenever it renders. Not designed yet: the PDF engine (Typst, light, or LaTeX, heavy), how a format item's words become a template setting, and where the render runs (pandoc is not on the box today).

The set-up box says it in one line each: Word: your assistant can read and check the draft. Markdown: your assistant can also write into it; no page count while you write.

4. How the checklist lives in a draft

Each heading the platform writes carries its checklist item's id as a marker: c + the item's 32 hex digits. One grammar, defined once in graph/docx.ts and imported by every format. The depth-to-heading mapping is one shared constant too: the task's title, then its parts, then sub-parts.

Markdown

# Project Description

**Limit: 20 pages maximum**

## I. Research and Capacity-Building Goals {#c9d91d545d8694…}

### B. Evaluation and Assessment Plan {#c70e1c460454d49…}

> *From the call:* Annual evaluation by an independent
> evaluator, EDOCS outcome collection, …

(the team writes here)

Word

<w:bookmarkStart w:name="_c70e1c460454d49…"/>
<w:p>
  <w:pPr><w:pStyle w:val="Heading2"/></w:pPr>
  <w:r><w:t>B. Evaluation and Assessment Plan</w:t></w:r>
</w:p>
<w:p>… grey italic: the call's words …</w:p>

A hidden bookmark on each heading; the level is the heading style.

A section runs to the next marked heading or the next heading at its level or above, so a writer's own sub-headings stay inside it. Markdown reads two marker spellings, the attribute {#c…} and the comment <!-- c… -->, until the hand test in Microsoft's editor says which survives. The attribute has one more property: pandoc carries it into a .docx as a bookmark today's Word reader understands, so a Markdown draft can be turned into a Word file that still maps to the checklist (prototype finding 1).

5. The tools

Plain functions in lib/server/proposals/agent.ts, listed in AGENT_TOOLS, served by the app's connector and callable in-process by the platform's agent. They follow the pattern agents already use on UVM's requirements: outline, then a section by id, then more of it.

ToolWordMarkdownWhat it does
checklist_readextended✓✓Adds each section's item id and marker, and each document's draft files with format and editable. Today section ids are dropped.
draft_outlinenew✓✓Per file: headings with item id, level, size. Items missing from the file, markers not on the checklist, unmarked headings, duplicates. Starts from the platform's links to the files, the listing of the task's folder (or, for a task with none, of the attempt folder's own top-level files, only the task's own: its provisioned links or named after it) confirms. A document task only.
read_draftextended✓✓Adds section (an item id) and offset; returns the section's version. Offset also works on files with no markers (uploaded PDFs, old Word). A section read costs 1, not 3.
update_sectionnewrefused✓Replace or append to an item's section, by item id, given the version it read. The main write.
add_sectionnewrefused✓Insert a missing item's heading, marker and guidance in its place; or adopt: re-mark an unmarked heading whose title matches a missing item.
edit_draftnewrefused✓Exact-string replace, scoped to one section: small corrections.

Cut: a draft grep. Outline, section and offset cover navigation; a search can come later on the same download if a need is measured.

6. How a write lands

  1. The agent reads the section with read_draft and receives its version: 8 characters, a hash of the section's text. No draft text is stored; the hash is recomputed from the file on every call.
  2. It calls update_section with the item id, the version and its text.
  3. The server refuses text that carries a marker, a heading at the section's level or above, or more than the size cap.
  4. It downloads the file now, finds the item's section, and compares its hash with the version. Changed: refused, "someone changed this section since you read it". Unchanged: the text is spliced in; nothing outside the section moves.
  5. It opens an upload session on the file with If-Match on the eTag it downloaded (Microsoft documents the 412 on that call, not on a plain content PUT), then puts the whole file to the session's pre-authenticated address, checked to be on sharepoint.com and never sent the token. If anyone saved in between (Microsoft's editor saves as people type), the server waits 200–500 ms, re-downloads and repeats from 4, three attempts in all. Only a change to this same section refuses. Left open: a save between the session's opening and the upload, which Microsoft documents neither way.
  6. One proposal_events row, type draft_written: who, which task, file and item, the tool, size before and after. Never the text. History shows it, the other parties' Updates feed carries it, and SharePoint's own version history shows the person as the author. If the row cannot be written, it is tried once more, then the answer and the operator's log say so.
  7. A write can still be lost afterwards: Microsoft's web editor saves what a person typed a short while later (the editor's autosave delay), so if someone had the file open with unsaved typing, their next autosave replaces the upload (it stays in SharePoint's version history; If-Match cannot see edits still in the browser). The agent's instructions therefore have it read the section again after a write, and write once more only if the section reads exactly as before its first write; if it holds the person's new words it stops and tells them, showing what it meant to put in. For an append it first checks its text is not already there. This check is the agent's best effort: a client cannot reliably wait, and an agent that re-reads at once sees its own write. A later step could have the server re-read recently written files on the token's next request and report a lost write (not built).

9. How it is delivered

As any developer's work: branches, tests against the fake drive and fake Teams (no test ever creates a real team), merge requests; the owner merges and deploys main to staging, then production. Code that writes to Teams meets a real team only on staging.

A. Reading first

The 0006 amendment (docs only), then: docx-read.ts returns ids with text, draft-files/ (Word), section ids in checklist_read (its file list from the platform's links, so it stays free of Graph calls), draft_outline, read_draft by section and offset (a per-tool cost that can depend on whether a section was asked, never logging an argument). No migration. Word teams benefit at once.

B. Markdown and writing

The 0006 addendum for writes (docs only), then: draft_format, Markdown outlines, the teams.ts PUT, update_section, add_section, the event row, the draft check reading .md (no page count). Off unless one setting turns it on, and that setting hides the whole Markdown surface: the set-up option, the write tools, the task page's buttons. Set in staging's environment only, so nothing in production changes until it is switched on there. It opens once the hand test (section 11) is in.

10. Built to be pruned

Shaped so that dropping any part later is deleting files, not a refactor:

  • The write tools in one file, proposals/agent-writes.ts, added to AGENT_TOOLS in one line.
  • One property on a tool, not lists of names: flag decides where it is served (generalising today's reviewers'-text switch), writes exempts it from the read-only transaction and records its event. A test: every writing tool carries the writes flag.
  • The formats in one registry constant, DRAFT_FORMATS; the set-up box renders its options from it and the server validates against it.
  • One setting for the whole Markdown surface, read in one predicate (beside the other environment rules in env.ts).
  • The column as plain nullable text: no Postgres enum, no default, null reads as Word.
  • One event type, draft_written, the tool, file, item and sizes in its details.
  • The connector's tool-list snapshot keyed by named configurations (default, reviewers, writes); the docs site renders default, so it never advertises a tool production does not serve.

Those have an exit: pandoc turns a Markdown draft with {#c…} markers into a Word file today's reader maps to the checklist, the reason the attribute spelling was worth its looks.

11. Open questions

Heavy checklists (queued 2026-10-27, after the gold labels, the overlap scorer and the parts fix). A complex call's key is long (RFAP: 28 deliverables, 130 rules, 67 form fields) mostly because of three kinds of row, each with its own home rather than a separate mode for complex grants: conditional items (a resubmission's response, a lobbying disclosure, collaborator letters) asked about and hidden when they do not apply, the biggest lever, since the key already records a condition per row and the drafter does not yet; rules folded under the deliverable they govern, the rest in one group for the whole application; form fields folded under their form, mostly SPA's. A complexity count (deliverables, conditional items, guide-sourced items) may serve as a signal, never as a switch. Nothing is built; it is the next design question once completeness is measured.

Review notes in a Markdown draft (being tried, the owner, 2026-10-28). A person's assistant leaves its review of a section in the draft itself, beside the passage it concerns: a blockquote spelled > [!note] horizon: … (GitHub's alert syntax, a callout where the editor renders one), put in with edit_draft (the passage replaced by itself and the note after it) or appended with update_section. No code: the guards allow it (a blockquote is neither a marker nor a heading), and the write is recorded as any other. Only on the person's request, through their own assistant; the platform writing notes on its own is the platform agent's own addendum (0006, the write addendum, 6). Two costs while it is tried: a note is draft text, so draft_outline's counts include it, and a note nobody deleted goes to the sponsor (pandoc keeps a blockquote visible in Word). If notes prove useful, the readers learn the spelling with no model: left out of word counts and limits, listed per section in draft_outline, and any still in the file flagged by the draft check. Microsoft's own inline comments for Markdown (roadmap 566202, general availability expected August 2026) are the other way: no Graph or SharePoint REST endpoint reads or writes a file's inline comments that we found (Microsoft's answer of 2025-08-18: none, none scheduled), so they reach the platform only if the editor stores them in the .md itself; the hand test below says which. The owner's view after the trial (2026-10-28): workable now, with the losses managed rather than prevented; two ways queued, neither built: reviews run while nobody is editing (overnight, on a schedule), and a write watched for about 30 seconds and made again if an autosave erased it (section 6, 7's "later step", done by the server). A scheduled review by the platform is the platform agent's addendum; one by a person's own assistant is not.

On staging, against real Graph (the fakes cannot answer these): is the upload address always on sharepoint.com; does a save between the session's opening and the upload get caught; does the upload's answer carry the new eTag; is the replace flag in the session's body needed.

The owner's hand test in a real team, with out/handtest.md from the lab:

  • Does the Markdown editor open from the Teams Files tab, or only in SharePoint and OneDrive?
  • Which marker spelling survives rewording and moving a heading in the editor? Is {#c…} shown as text?
  • Do co-authoring and comments work; is there a suggestion or tracked-changes mode? (Co-authoring works, 2026-10-26.) Add an inline comment, download the .md: is the comment in the file?
  • While someone has the file open: does a new version uploaded over it merge, fork a copy, or get refused? How often does the eTag change while someone types? Answered by the owner's trial of review notes, 2026-10-28 (Claude Desktop over the connector, a file per deliverable): the notes land and are recorded; an editor open on the file does not take in the agent's write until the page is refreshed (a co-author's typing shows live); a write landing while someone types is erased by their next autosave. Not observed directly: whether an idle editor's next keystroke, much later, saves over it too (likely, as it never took the write in).
  • Does the editor save Windows line endings? (The write path normalises them either way.)

And for the PDF step (section 3): which engine, how format items become template settings, and where the render runs.

12. Words

Item
A checklist row: a deliverable the sponsor wants, or a part or sub-part of one.
Deliverable
Anything in the application package: a file or text field the team writes (written), a file it collects (collected), or a form it fills in the sponsor's system (form). The thing produced, never the sponsor's form; the form and field are its submitted_as (decision 0006, addendum 2026-10-26 on deliverables, 1).
Marker
The item's id on its heading: c<hex32> in text formats, a hidden bookmark _c<hex32> in Word.
Section
The text that belongs to an item: from its heading to the next marked heading or the next heading at its level or above.
Version
A short hash of a section's text, returned by a read and required by a write.
Connector
The app's own MCP server at /mcp, for a person's own AI assistant (decision 0012).
Party
Someone with a role on the proposal: owner, team member, routed SPA administrator, the RD who claimed it.
Hand test
The owner trying the Markdown file in a real Teams workspace; it settles what a local prototype cannot.
