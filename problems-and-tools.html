Problems first, then tools

How to decide which tools horizon should have. Start from the questions people at UVM bring, find the calls a good assistant would make to answer them, and leave the judgment to the model and a skill. Each idea is shown on horizon's own tools.

Part 1. Ideas

1. What a tool returns

MCP's introductions explain tools with a trip. One assistant reaches three servers and calls searchFlights(origin, destination, date), then createCalendarEvent(...), then sendEmail(...). The person asked for one outcome, and the assistant chose the calls.

Anthropic's write-up on advanced tool use has an example closer to a university's: "Which team members exceeded their Q3 travel budget?" It gives the model three tools: get_team_members(department), get_expenses(user_id, quarter) and get_budget_by_level(level). Three things make them the right size:

  • Each returns domain records, such as a person, an expense line or a limit, in the institution's own terms.
  • They chain by id. The user_id that one returns is what the next one takes.
  • None of them answers the question. The model compares the expenses with the limits.

horizon follows the first two rules and bends the third on purpose, in two ways.

Arithmetic goes in a tool

A model can get a sum, a cap or a rate base wrong. Decision 0025, item 2 makes budget_compute the one authority for budget arithmetic, so every client gets the same numbers. A skill never carries a script that computes a budget.

Some judgments go in a tool

opportunities_eligibility returns a verdict per requirement, and opportunities_match returns a ranking. A model could not make either as well alone, because each needs the whole corpus, a reviewed rule or a benchmarked model. Each verdict carries the quote behind it, and none decides for the person. A ranking is not a recommendation to apply, and a verdict is not SPA's ruling.

Words like "fits", "realistic", "risky" and "ready" stay with the model. A skill says how to reach them.

2. An answer, not an inventory

Anthropic's Writing tools for agents warns against tools that hand a model everything to filter or join. Its examples replace list_users, list_events and create_event with one schedule_event, read_logs with search_logs, and three customer lookups with one get_customer_context. A tool named _list is not the problem. A tool that returns an inventory where the person wanted an answer is the problem, and so is a chain of calls the server could have made in one.

horizon has both kinds:

  • checklist_read with a proposal_id returns tasks, status, the sponsor's quotes, required documents and eligibility in one reply. That is the get_customer_context shape.
  • draft_read's outline lists open_findings and changed_since_check, so the model knows where to look first. That is the search_logs idea.
  • "Where does my proposal stand?" takes five calls today. The proposed proposals_read answers it in one.
  • documents_list returned up to ten years of synopses for a call. !227 trimmed it. The open question is whether search should come before list.

The verdict on each tool is in tools-skills-mcp.html.

3. Split writes by who approves them

Fewer tools are easier for a model to choose between. draft_edit takes an action instead of being three tools, and draft_read with no section returns the outline. Anthropic's tool guidance does the same with pull requests, using one tool with an action instead of create_pr, review_pr and merge_pr.

Writes are the exception. A client approves and annotates a tool, not an action, so a write tool should group only the actions a person would approve the same way. Editing your own draft, sending SPA a routine request and submitting a proposal are three tools for that reason. A person who always allows the routine request has not allowed a submission. The proposed write tools (proposals_edit, proposals_route, proposals_submit, checklist_edit) follow this rule, and each needs an addendum to decision 0006 before anyone writes its code.

4. Documents and records

Document-shaped

These are the requirements and documents tool families. A model searches a corpus, reads a passage and quotes it with its date and source. These tools answer "what does the rule say?" Most of what horizon serves is this kind.

Record-shaped

These are entities with ids and numbers that a model can join and compare, such as proposals, checklist items, eligibility verdicts and, from decisions 0024 and 0025, facts and budgets. These tools answer "is this budget realistic?", which no passage search answers, however good it gets.

Decision 0024 turns a document into records where that matters. A fact such as UVM's fringe rate or a funder's salary cap becomes a value with the sentence it rests on, its source, its dates and whether SPA has confirmed it. The sentence keeps what made the document tools trustworthy. The value makes it something a tool can compute with.

A record tool raises its own question, whether to merge parts or split them. Without code mode, every call is a round trip through the model, so merging parts that are always used together saves calls, such as one awards_read that carries the award's terms. With code mode, small tools chain at low cost in a sandbox and large results never reach the model. the rule this page proposes is to merge parts that are always used together and are small, and to split parts that are used selectively or can get large. Spending transactions are the second kind.

5. Strong tasks and weak tasks

Anthropic separates strong evaluation tasks from weak ones. A strong task states an outcome, takes several calls and leaves room for judgment: "Customer 9182 was charged three times. Find the log entries and whether other customers were affected." A weak task is one call: "Search the payment logs for customer_id=9182."

Strong tasks decide the tools

A tool earns its place when a strong task needs it. Strong tasks are also what an agent-level benchmark keys and grades (evaluation.html).

Weak tasks are a tool's own tests

"Get the call with id X" has one right answer, so it gets a deterministic test. The house rule says the same. Ranking and judging tools get a keyed benchmark, and lookup tools get a test.

6. Two kinds of skill

Anthropic's guide to building skills names two starting points.

Tool-first

The person already has the tools, and the skill teaches how to read what they return. uvm-requirements, the one skill the plugin ships, is this kind. It teaches quoting the revision date, telling UVM's half from the funder's, and saying "my results don't have it" instead of "UVM has no rule".

Problem-first

The person describes an outcome, and the skill makes the calls in order and says how to reach the judgment. Decision 0025 planned the first, budget-build, and it shipped in the same branch as budget_compute (!238). The others are candidates (tools-skills-mcp.html).

Every client sees a tool's description and, nearly every client, the server's instructions. Only some clients load skills. So a sentence an outside user's assistant cannot do without goes in the instructions or a description, and a sentence that makes a good answer better goes in a skill.

The MCP specification adds a third place. A server can serve prompts, which are workflows a person starts by picking them as slash commands. A problem-first workflow is something a person asks for, so it fits a prompt better than a skill the model has to decide to load. A prompt reaches every client that supports prompts without a plugin. Tool-first knowledge stays a skill. The split, on the draft check, is in tools-skills-mcp.html. proposed

  • Outcomes and inventions. "Which awards produced papers but no invention disclosure, in areas where UVM Innovations has licensed before?" These need the outcomes and inventions domains that AGENTS.md lists for later.
  • Analytics. These are for offices and deans. "NIH submissions from my college dropped this year. Where, and why?" These cross domains, so they are dbt marts behind one or two query tools rather than new record tools.

11. Worked example: the budget question

"Is this proposal's budget unrealistic given its narrative and the program solicitation?" A first draft of this page answered it with six calls: read the proposal, read its budget, read the call's limits, look up the rates, run the checks, compare with funded awards. Decision 0025 settles it differently, as the list below shows.

  1. proposed budget_compare (account, 0025 addendum A4) takes the proposal_id. It reads the team's workbook and the Summary Proposal Budget through the documents tools' proposal half. It uses readers of their known layouts, not a model. It reports where they disagree with each other, with the call's limits and with the justification.
  2. served budget_compute (Low, 0025 item 5) takes a budget in the budget-1 shape, and may take the call_id, which reports the call's limits by name (addendum C1). It checks none of them yet. It looks up UVM's and the funder's rates itself, in funding.facts, and returns the totals per period and a checks block, each check naming the fact it rests on.
  3. served draft_read for the narrative's aims and activities.

Why the rates are not a separate step. In the first draft the model called a rate tool and passed the numbers into the calculator. Decision 0025, item 4 forbids that: "a model never passes a rate in, so a budget question is one call, not facts_read then budget_compute with numbers copied between them." A model makes mistakes when it copies a number between calls. facts_read stays for questions about a rate itself.

Where the judgment stays. Does 10% effort fit a PI who owns three of four aims? The narrative describes fieldwork, so why is there no travel line? The checks find what breaks a rule. The budget-build skill and the model judge what is unusual, and say which findings are rules and which are opinions.

The engine, built and tested in frontend/src/lib/tools/budget/ (!237), and the tool budget_compute (!238) are served, with the budget-build skill shipped beside them. The figures and reference tables are on budgets.html.

12. The order to build in

Four questions score each strong task:

  1. Is the data in hand, and is it Low? Public data needs no account and reaches outside users on their own assistants.
  2. Can the answer be keyed? A judgment that cannot be graded cannot be improved.
  3. Does someone at UVM ask it every week? Ask SPA and the research administrators. Usage of the unlaunched site is not evidence.
  4. Does it reuse tools other stages need? facts_read serves every stage that touches a rate or an identifier. A spending feed serves post-award only.
