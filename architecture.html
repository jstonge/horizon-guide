1. What horizon is

The University of Vermont keeps the data about research funding in separate places: funding opportunities, researchers, proposals, awards and inventions. horizon joins them, so that finding funding, preparing a proposal (pre-award), managing an award (post-award), commercialization and analytics all work from the same record.

A warehouse

A PostgreSQL database that a pipeline fills. The database is organised by domain and by UVM's data classification, and the pipeline keeps every version it fetched.

Tools over it

The app serves one MCP endpoint, /mcp, in its own process, so people and their AI assistants can query the warehouse. It has 15 tools in five families: UVM's rules, funding opportunities, a call's documents and funder guides, budgets, and a person's proposals and drafts.

Skills with them

An assistant loads these written instructions to use the tools. People get them in the Claude Code plugin, and developers get them in .agents/skills/.

Products on top

The pre-award app comes first. In it, a person discovers funding, builds a proposal with its checklist and routes it to the people who help.

horizon was rebuilt from an earlier app, svelte-CODEC, which is now a read-only archive. The owner declared parity on 2026-10-17, and production moved to horizon on 2026-10-19.

Tools, skills and evals first

horizon is built in an order: the data, then tools over it, then the method for using them, then measurement, and the product last. Its own page explains why, and how that differs from the Codec prototype's feature-first build.

4. The pipeline

The pipeline is one Python package with stages, lowest first. A stage may import only the stages below it, and make verify checks that.

  1. store: the database access every stage shares.
  2. fetch: Sources, the code that talks to a system we do not run. Every fetch lands in raw and is kept. History is never pruned (decision 0002).
  3. read: Readers, which turn a fetched page or record into text, blocks or sections. Readers convert documents with docling.
  4. enrich: models over our data, such as eligibility answers, a document's use cases, search vectors and grant-matching suggestions.
  5. load: writes the results back.
  6. defs: the Dagster assets, checks and schedules, one file per domain.

Each stage has the same domains: opportunities, researchers, match, requirements, proposals, awards, peers, reference, plus institutional for SharePoint. Domains never import each other. A dbt mart answers a question that crosses domains by joining through the reference tables (people, units, sponsors).

dbt turns the raw rows into the tables the products read: staging (one clean view per source), then intermediate, then marts in the schemas funding, people and requirements. The marts the tools and the app read carry dbt contracts, so a change to their shape fails the build.

At 98b7a9b6 (2026-11-02) the pipeline has 207 Dagster assets with 645 checks, and dbt builds 110 models, 71 of them marts (Data sources has the counts).

Dagster runs it all. A raw source is one asset with its checks (fresh, schema drift, duplicates). A model lane has one shape: <domain>_jobs_pending → <domain>_<lane>_run → <domain>_<lane>_loaded. Schedules are allow-lists in defs/schedules.py: a daily ingest, dbt at 07:00, the checks two hours after the ingest, and weekly, monthly or quarterly runs for the slow sources.

5. Data and its tiers

horizon uses UVM's data risk classification: Low, Moderate, High, Restricted. It holds nothing above Moderate (decision 0003). One rule shapes the whole database. The tier is the schema. A table's tier is the schema it lives in, and a person or a process that may not see a tier holds no access to its schemas at all.

TierSchemasWhat is in them
Lowraw, staging, enrich, funding, people, requirements, curation, evals, mcpPublic sources and what models derive from them: opportunities, UVM's published rules, public research records, benchmark keys, the service tokens and the tools' spend.
Moderateapp, governance, institutional, matchingThe product's records: accounts, proposals and their documents, sessions, model-call ledgers, SharePoint content, per-person matching.

Each process has its own database role: pipeline (one daemon, every tier), mcp (Low only, used by the published tools), web_app (the app, which applies its own access rules to Moderate rows). Outside production, Moderate data is synthetic: seed personas, never real people (decision 0006). make tiers-check enforces the grants.

6. The tools

The tools live in frontend/src/lib/server/tools/.

An MCP endpoint lets an AI assistant call tools. horizon has one, /mcp, which the app serves in its own process. It has 15 tools in five families:

  • UVM's rules: uvm_requirements_search, uvm_requirements_read, uvm_requirements_outline and uvm_requirements_units.
  • Funding opportunities: opportunities_match to find the calls that fit some work, and opportunities_eligibility and checklist_read to judge one call.
  • A call's documents and funder guides: documents_list, documents_search and documents_read.
  • Budgets: budget_compute.
  • A proposal and its drafts: proposals_list, draft_read, draft_edit and critiques_list.

Published tools read Low data only. Account tools need a signed-in person and read that person's own Moderate rows. Search combines keyword search, vectors and a reranker. Every reply is the envelope {status, message, ...}, and every search reports which lanes ran and which fell back, so a degraded answer always says it is degraded.

A person mints an hzp_ token in the app's Settings while signed in with their NetID, then adds the connector to their client (decision 0012). Services get operator-minted tokens (prefix hzn_, NetIDs svc_*) that reach only the published tools. There is no anonymous access from outside the box. The headless host on loopback takes anonymous callers in development only. The app's hostname is reachable on the UVM network or the VPN. docs/mcp-connect.md explains how to connect. Tools, skills and MCP lists every tool and says what each one is for.

Two decisions, both accepted, add budgets. Decision 0024 makes a fact a reviewed value that keeps the sentence it rests on. Decision 0025 puts one budget calculator in front of SPA's entry of the budget in UVMClick, which stays the record. Merge request !237 built and tested the calculator, the budget engine, in frontend/src/lib/tools/budget/, and budget_compute serves it (merge request !238).

More: the tool inventory, where it lives in the code, Budgets, connecting to the MCP, decision 0023 on one tool layer.

7. The skills

A tool says what it does. A skill is a set of written instructions an assistant loads to reach a person's goal with several tools, and to judge how far to trust their answers. horizon ships skills to people who use the tools, and keeps its own for the developers who build them.

WhereWho it is forWhat is there
plugin/skills/People using the tools from Claude Codeuvm-requirements: how to read UVM's rules without overstating them (quote the revision date, keep UVM's half apart from the funder's, and treat a scan that cannot be read as held, not missing). budget-build: how to build and check a proposal budget with budget_compute, shipped with it in !238.
.agents/skills/Developers and their agents working on horizonexperiment-ledger and experiment-report (how to record and show a benchmark run), unslop (the writing rules), and the third-party shadcn-svelte, pinned in skills-lock.json.

A person gets the user skills by installing the Claude Code plugin in plugin/, which also holds the /mcp address and asks for the token. Claude Desktop takes no plugin, so its users add the skill by hand (decision 0023, item 12). The MCP specification now lets a server serve skills itself, but the Claude clients do not load them that way yet, so the plugin remains how skills reach people (owner, 2026-11-02).

The app uses the same text. The app builds the requirements chat's system prompt from uvm-requirements's SKILL.md, minus the sections about calling tools (frontend/src/lib/server/answer/prompt.ts), so the chat and an outside assistant follow one set of rules. A test fails when a skill names a tool or a field the server does not serve, or when a served tool appears in no skill (frontend/tests/tools/skill.test.ts).

A workflow a person starts, such as reviewing a draft against the call, may move from a skill to an MCP prompt the server serves itself. Claude Code lists a server's prompts as commands, so the workflow would reach people without the plugin. That is proposed, not ruled (where a tool stops and a skill begins).

10. Measuring: evals and MLflow

A benchmark judges a change to retrieval or to a model lane, not a person's eye. Each benchmark is a folder in evals/: the requirements gate (does search find the right passage?), awards matching, eligibility, and the proposal checklist. A benchmark runs against a frozen dataset and logs a run to MLflow, the experiment tracker (horizon-mlflow on the box).

  • Cite a number with an MLflow run id or a committed findings/ output, or do not cite it.
  • A run is recorded (from a clean commit, citable) or routine (your scratch).
  • MLflow holds the record: parameters, metrics, the dataset's sha256. The bytes (datasets and raw outputs) live in the data root $EVALS_DATA_DIR, split by tier, never in git.

More: Evaluation, docs/evals/README.md, evals/AGENTS.md, docs/evals/design.md, decision 0018 on where benchmark data lives.

11. Where it runs

Everything runs on one UVM virtual machine, codec-dev, under pm2, except production's database, which is on codecdb.uvm.edu. docs/release.md has the details.

ProcessWhat it isDatabase
horizon-webThe production app, which serves the tools in processproduction, on codecdb
horizon-web-stagingA box-local copy of the app over synthetic data, for pre-release checks and demoshorizon_staging
horizon-dagster, horizon-dagster-uiThe production pipeline and its UI (loopback only)production, on codecdb
horizon-mlflowThe experiment recordhorizon_mlflow

Development databases live on a local PostgreSQL 18 cluster on port 5433: your own horizon_dev_<you>, a throwaway horizon_wt_<name> per worktree, and the shared ones (horizon_dev, horizon_staging) that only the operator writes.

The word "staging" has two meanings, so check it. Production's public hostname is staging.codec.uvm.edu, so "staging" in a URL means production. The process horizon-web-staging and the database horizon_staging are the synthetic copy on the box, reached only through a tunnel.

12. How work gets done

  1. Work on a branch in your own git worktree, never in the main checkout.
  2. Give the worktree its own database: make wt-db NAME=<name>, and export the DATABASE_URL it prints.
  3. Run make verify. It runs the checks for what your branch changed, and the pre-push hook runs it again.
  4. Push the branch and open a merge request. CI runs the same checks.
  5. The owner merges and ships to production. Agents never start pm2, deploy, or touch production.

A schema change is a migration: alembic for the pipeline's schemas, Drizzle for the app's. Its merge message lists the operator steps that upgrade the shared databases.

13. Words you will meet

Source
Pipeline code that fetches from one outside system and lands it in raw.
Reader
Pipeline code that turns a fetched page or file into text, blocks or sections.
Lane
A model step in the pipeline (an enrich lane), or one stage of the tools' search (the rerank lane).
Mart
A finished dbt table the products read.
Tier
UVM's data classification (Low, Moderate); in horizon, the schema a table lives in.
Gate
The requirements benchmark a retrieval change must pass.
Arm
One configuration in a benchmark, compared with its parent.
MCP
Model Context Protocol, which an AI assistant uses to call a server's tools.
Published tool
A tool that reads Low data only and answers for anyone who may connect, such as uvm_requirements_search.
Account tool
A tool that answers for one signed-in person and reads their own Moderate rows, such as proposals_list. It refuses a call with no account.
Envelope
The shape of every tool reply: {status, message, ...}. status is ok, not_found, refused or truncated, and message is one sentence that gives the next step.
via
Where a call came from: assistant for a person's own assistant over /mcp, platform for the app's own pages calling the tools in process.
PI
Principal investigator, the researcher leading a proposal.
SPA
Sponsored Project Administration, UVM's office that submits proposals and manages awards.
RD
Research development: staff who help researchers find funding and shape proposals.
VACC
The Vermont Advanced Computing Center, UVM's cluster with the GPUs.
The archive
svelte-CODEC, the app horizon was rebuilt from. It is read-only.
