Tools, skills, MCP

What a person's assistant can do with horizon today, in three layers. Tools look things up, read texts and write drafts. Skills give the order to call the tools in and say how to judge what they return. MCP is the protocol any assistant uses to reach the tools.

How to read this page

Part 1 lists the tools by family: what each returns, an example call, and what a signed-in person gets beyond a service. Part 2 lists the skills we ship and the ones our tools could carry. Part 3 says how a request reaches the tools and which parts of the MCP specification we use.

A question such as "Can my lab apply to this call, and what must we hand in?" takes tools from several families. The model chains them by the ids each returns (1.7). The ideas behind the families (records with ids, answers rather than inventories, writes split by who approves them) are on problems-and-tools.html.

A write groups the actions a person would approve the same way. The audit and !185 name one candidate per action on a page; the names below are this page's, not theirs.

Who wrote it, and what it attaches to

A call's scope mixes texts by different authors. The author tells a model how much weight a text carries: a funder's rule, UVM's rule, or someone's advice. What the text attaches to decides which scope finds it. How it arrived, crawled or uploaded, decides neither.

Who wrote itAll of UVMA funder or programOne callOne proposal
UVMThe requirements corpus, crawled gap SPA's own checklist for NSF proposals, its tips for NIH Staff uploads, such as a checklist for this call
The funder Guides and notices, crawled (decisions 0014 and 0021) Solicitation, amendments and FAQ, crawled
Others Staff uploads, such as last year's reviews or a funded proposal The team's drafts and uploads, the reviewers' critiques

The gap is UVM's own material about a funder. Today it lives in the requirements corpus only if UVM publishes it on www.uvm.edu. Otherwise staff upload it call by call, because a guide's scope takes no uploads. Three changes would close it. proposed

  • Staff can attach UVM-written material to a funder or a guide. It then appears in the scope of every call that inherits that guide, and stays labelled as UVM's words.
  • Every upload states its kind and its author, such as staff checklist, past reviews or prior proposal. A model then never quotes last year's reviewer as the funder.
  • Funder guides stay crawled and apart from UVM's corpus, as decision 0014 ruled. Whether they become a tool family of their own or stay a scope of the documents tools is a question decision 0023's addendum leaves open. This page leans to keeping them a scope, since one search over a call already reaches its guides.

Part 2. Skills

A tool says what it does. A skill says how to get a person's outcome out of several tools, and how far to trust what they return. A tool-first skill teaches how to read one family's results; a problem-first skill makes the calls for an outcome (problems-and-tools.html).

2.1 What we ship today

The Claude Code plugin ships two skills, uvm-requirements and budget-build, in plugin/skills/. uvm-requirements is tool-first. Most of its text teaches how to read results, not which tool to choose:

  • A real question has two halves, the funder's and UVM's, and these tools hold UVM's half only.
  • Quote the revision date with every rule. These procedures date from 2018 to 2026.
  • A scanned letter that cannot be read is held, not missing. Give the link and state no value from it.
  • "My results don't have it" is not "UVM has no rule". Search again before saying so.
  • Off the corpus, a UVM page is a source and a third-party aggregator is not.

budget-build builds or checks a UVM grant proposal budget with budget_compute, including what-ifs. It tells the model never to do a budget's arithmetic itself or copy a rate from a web page, and to say that SPA enters the final budget in UVMClick.

The uvm-requirements skill's list of which tool to call when repeats what the server's instructions and each tool's description already say. That part could shrink to a pointer. A test, frontend/tests/tools/skill.test.ts, fails unless some skill names every served tool, so shrinking it needs a ruling.

Where a tool stops and a skill begins: the draft check

The MCP specification sorts what a server offers by who decides to use it (server features):

A skill sits beside these. It is not part of MCP. The person's client loads it, and the model uses it when the conversation calls for it.

Two questions describe any feature. Who starts it: a person in the app, a person in their own assistant, or the model on its own. Where the judgment is made: on horizon's server, by our model, kept and measurable; or in the person's client, by their model, gone when the conversation ends.

So a tool hands over facts and judgments already made and kept: the draft's sections, the checklist, the sponsor's words, the last check's findings. It never judges for this conversation. The server makes any judgment the team relies on, because that judgment has to be the same for everyone, recorded and measurable. It reaches an assistant as a record through a tool. A workflow a person starts from their own assistant is a prompt. Knowledge the model needs whenever it touches a family of tools is a skill, with its must-know lines also in the server's instructions.

One method per judgment. The draft check's method lives in the app (lib/server/drafter/draft-check.ts), and only the app's runs are kept, so only they could be benchmarked. A prompt or skill that re-derived the same judgment with its own wording would be a second, unmeasured method that drifts. The client side reads the server's findings and adds only what it labels as its own.

The same holds for the other app runs. The checklist drafter and Compare with reviews reach an assistant through checklist_read and critiques_list. The mock review panel's results reach no tool yet.

2.3 What goes where

The same sentence could live in a tool's description, in the server's instructions, in a skill or in a reply's message. Which clients see each place decides where the sentence goes.

PlaceWho sees itWhat belongs there
Tool descriptionEvery MCP client, whenever the tool is loaded. Claude Code may load it only when a search finds it, and cuts it at 4,096 characters, or 16,384 when found by search.What the tool does, when to use it, when not, what to call next. Words a model would search for, near the start.
Server instructionsMost clients, at connection. Claude Code loads them even with tool search on, and cuts them at 4,096 characters.Which family answers which question, the reply statuses, and the few rules an assistant must never break.

Rule of thumb. If an outside user's assistant gets it wrong without the sentence, the sentence goes in the instructions or the description, because those reach every client. If it makes a good answer better, it goes in a skill.

Part 3. MCP

The app serves one address, /mcp, in its own process. Any MCP client reaches the tools there, and the plugin adds the skill for Claude Code.

3.1 One request's path

  1. Connection. The client sends a bearer token with every request. A person makes an hzp_ token in the app, and a service gets an svc_ token from the operator. The plugin sets the address and asks for the token.
  2. Discovery. A 2026-era client sends server/discover and gets the server's identity and instructions. A 2025-era client sends initialize and gets the same. The server answers both eras on one URL.
  3. The list. tools/list returns the tools this caller may call: eight for a service, all fifteen for a person with both switches on. Each tool carries its description, input schema, annotations and anthropic/maxResultSizeChars. The published tools and their variants also carry a loose output schema.
  4. The call. Every tools/call goes through callTool, which checks the input, checks the caller against the tool's account field, opens a read-only transaction for an account tool, runs the handler and wraps the reply.
  5. The reply. The reply is the envelope {status, message, ...} as text, with the same JSON in structuredContent. A not_found or refused reply also sets isError.

The app's own pages, such as the Ask tabs and the drafter, call the same tools through the same callTool, without MCP. A call records whether it came from the person's own assistant or from the platform (via).

What our replies cost the caller

Every reply lands in someone else's context, and an outside user's assistant pays for it. Anthropic's cost cookbook asks tool authors for narrow accessors over dumps, with parameters that trim a reply before it reaches the model. Our tools mostly do this already: types, limit and offset, replies cut at 12,000 characters with a truncated status that says where to read on, and since !227, no synopsis for a year whose texts are listed. The tool list keeps one order and one shape through a conversation, so a client's prompt cache over it stays valid. The cookbook also says not to restate the tools in the system prompt. That fits our Ask tabs, which load every tool and get the routing text as their system prompt. It does not fit Claude Code, where tool search defers our tools and the server's instructions are what tell a model when to search. What each reply costs, and what a whole task costs, is measured on evaluation.html.

3.2 What we use of the spec

This table compares horizon with the MCP specification of 2026-07-28 and the TypeScript SDK 2.4.0, the one the app runs.

Spec featureStatusHow
Stateless serving, both protocol erasin use The server builds one McpServer per request. The SDK's handler answers 2026-era requests, and an endpoint we wire ourselves answers 2025-era ones in plain JSON. The gate already speaks 2026.
Server instructionsin use They say which family answers which question and what each status means, then add each family's own text. Claude Code cuts them at 4,096 characters, so the important part comes first and frontend/tests/agent-instructions.test.ts holds them under the limit (decision 0023, addendum 2026-10-31, item 16).
A tool list that differs by callerin use The spec allows this. The list "MAY vary by the authorization presented on the request". The SDK's default cacheScope is private, which is right for it.
outputSchema and structuredContentpartial The published tools and their variants advertise loose schemas. The documents tools as the app serves them, and the account tools, advertise none yet.
Annotationsin use Every tool states its annotations. All are read-only except draft_edit, which is destructive and not idempotent. Claude Code runs read-only calls in parallel.
Authorizationour own The spec makes OAuth optional. The person puts the token in their client's configuration, so in Claude Code a bad token shows as a failed connection, not as a sign-in prompt.
