1. Anthropic's method

Anthropic's Writing tools for agents builds tools around an evaluation loop, not after one:

  1. Write many tasks from real use, each with an outcome that can be checked. Strong tasks state an outcome, need several calls and leave room for judgment. Weak tasks are one call in disguise. The examples problems-and-tools.html quotes in section 5 come from here.
  2. Run each task as an agent loop with the tools, and have the agent say what it is doing before each call.
  3. Collect the metrics: whether the answer is right, runtime, the number of tool calls, tokens and tool errors.
  4. Read the transcripts. Redundant calls point at a missing filter or a reply that is too long. A wrong tool points at a description. An error the agent could not recover from points at a message.
  5. Improve the tools, with Claude's help if useful, and check the change against held-out tasks so the tools do not fit the tasks they were tuned on.

Anthropic's cookbook Cost optimization on the Claude API starts from the same place: get the task working on a capable model, then build an eval that measures both pass rate and cost per task, set a baseline and a quality bar, and only then lower costs. Its levers, in the order it applies them, from least to most risk to quality: prompt caching, input size (narrow tools, deferred tools), context in long agent loops, output shape, batching, and last the model and its effort. A lever is kept only if the pass rate holds.

2. What horizon measures

Horizon measures what a tool returns, carefully. It does not yet measure what an agent does with it.

docs/evals/design.md, section 5, names two levels for every tool, in order, and a third for later:

LevelThe questionHow horizon answers it
ComponentIs the core's output good? A benchmark: a frozen dataset of keyed questions, arms read against their parent, recorded runs in MLflow. Four exist, in section 3.
ContractDoes the tool keep its promises: its schema, honest lanes, latency, cost, evidence on every row? Tests, mostly with no labels. A lookup tool gets only these: the documents tools, uvm_requirements_read, _outline and _units, and draft_read's 12,000-character cap.
AgentDoes an agent using several tools finish a task? Not measured. design.md calls it later: "traces, a Moderate experiment, restricted".

The agent level is where Anthropic's method lives, and where this page's open questions sit: search-first routing, whether proposals_read saves calls, whether the rewritten descriptions changed which tool a model picks, and whether a skill helps.

3. The four benchmarks

Each lives in evals/<subject>/<name>/ with a BRIEF.md (the question, why, the bar), a frozen dataset and a ledger of its recorded runs.

uvm_requirements_search: the requirements gate

Question. For a question a researcher asks, does the tool hand back the documents that answer it, and does the text it hands over hold the facts the answer needs?

  • Dataset: 204 questions with 727 required facts, key version 2026-10-05b, authored at /grading, split into held-out and tuning questions.
  • Bar (owner, 2026-10-21): required facts held, paired per question against the parent with a 95% interval, top-1 not significantly worse.
  • Recorded: arm 0, the tool as served, holds 534 of 727 facts with 162 questions right at top-1: run 57c3a9ad6125400f9f9550c002c0a219.
  • Also: a Claude-session judge grades whether a run's hand-over states each fact (evals/requirements/judge.py). Most current settings were measured in the archive on older key sets; the brief's table says which.
  • Limit: facts held measure the hand-over, not the answer a model gives.

opportunities_match: the awards benchmark

Question. Given the papers a UVM researcher published before an award, does the matching pipeline rank the call that funded it in its top 10?

  • Dataset: awards-2026-10-20.
  • Bar (spec 1): recall at 10 no more than 2 points below the parent, with a log-rank guard; an interval that straddles the bar is inconclusive.
  • Status: exploratory, no shipping decision. The baseline is arm 1, run f046016e70b44c7ba4e95e1a0e2cc26b. A smaller embedding model and dropping the reranker were rejected or inconclusive against it (evals/opportunities/matching/LEDGER.md).
  • Limit: arms run through rank.py, a copy of the pipeline held to it by a parity test, until the runner calls the tool itself.

opportunities_eligibility: pass 1

Question. Before any proposal exists, how much can the platform filter out for a user, and how often does it hide a call they could apply to?

  • Bar (decision 0013, item 9): no hard error, and at the default threshold hide at least as many open calls as the parent without wrongly hiding more awarded calls.
  • Status: draft. Routine runs only, none recorded, so no number is cited. The trust sample, the person table and extraction stability are one-time findings under findings/2026-10-21-*.
  • Open: the default threshold.

checklist_read: the checklist drafter

Question. Given a call's documents, does the checklist hold everything a UVM team must produce or do, each item quoting its source?

  • Dataset: keys for eight calls (2026-10-28d), four of them measured. The other 22 keys wait on documents.
  • Bar: deliverables recall is the headline. Owner, 2026-10-26: no drafter change may lower strict section recall or lose grounding, and every merge request that changes the drafter cites its recorded run.
  • Recorded: !81, the documents pass asking for the online form's narratives, raised deliverables recall from 0.85 to 0.87 and strict section recall from 0.61 to 0.73, and was adopted: run 940f7e612ee142728fa42e6ac97e17c1. !80's parts prompt raised coverage but lowered strict section recall, so it was not adopted: run 9be8395f6dcb49399b3045e093259a96.
  • Limit: one draft per call, so a few points sit within run-to-run variance.

One benchmark was retired: the call-reading benchmark for the draft tools, on 2026-10-29. A deterministic test of the 12,000-character cap replaced it, under the rule that lookup tools get tests and ranking or judging tools get benchmarks.

5. Pass rate and cost, tool by tool proposed

A pass is one item, judged yes or no. A benchmark's recall becomes a pass rate once the bar says what one item must reach.

Our benchmarks report averages, such as facts held or deliverables recall. The cookbook's pass rate counts items that clear a stated bar. Both can come from the same run: the average says how far a change moved things, and the pass rate says how many items a person would be satisfied with. Where the line sits for each tool is the owner's call; this section proposes one.

Two kinds of cost

The caller's agentThe tokens our replies add to someone else's context, and the calls a task takes. An outside user's assistant pays this. Reply size in characters and tokens, calls per task, from the transcript.

Per task, at the agent level

A task passes when its answer states every keyed fact, attributes each to the right source (the funder's half or UVM's, with its date), and contradicts none. The facts it states are counted too, so a near miss shows. Its cost is the agent's tokens, its calls, and the tools' own spend for those calls. This is the number the cookbook asks for before any cost lever: a pass rate and a cost per task, on the same tasks, so a cheaper setting is kept only if the pass rate holds.

Cost levers wait for this. Prompt caching in the Ask tabs and the drafter is the cookbook's first lever and is not on today: model/client.ts counts cached tokens, but no request sets cache_control. The owner put it off on 2026-11-01 until an eval measures pass rate and cost per task, so its saving can be shown and its quality checked.

6. The missing level: agents proposed

One task set, measured end to end, reused for every change to tools, descriptions and skills.

Why not yet, so far

The owner refused two narrower measurements. The call-reading benchmark was retired on 2026-10-29. A five-question measurement of folding uvm_requirements_outline and _units into search was refused on 2026-10-30 as too small to tell two designs apart. Both measured one tool decision. An agent-level set would measure every later change to tools, descriptions and skills with the same tasks, so its cost is paid once.

The design

  • Tasks: twenty to thirty strong tasks, drawn from the problem-first skills in tools-skills-mcp.html, section 2.3: find-funding, prepare-to-apply, draft-check, resubmission. Each has facts a script can check: the right call id, the quoted sentence, the date given with a rule, the funder's half and UVM's half kept apart.
  • Low first. Tasks over published data need no account, so the set and its transcripts are Low and run anywhere. Tasks over a proposal come later, on synthetic proposals in a worktree database, as design.md's Moderate experiment.
  • Held-out: a split, under the gate's honour rule.
  • Run: headless Claude Code (claude -p) on the subscription, against the make tools-dev host the gate already uses, with and without each skill.
  • Record per task: whether it passed (section 5's task rule) and each keyed fact, then its cost: the agent's tokens in and out, the tool calls, which tools in which order, the tools' own model spend and tool errors. A recorded run with each transcript as a trace, so two runs line up task by task.
  • Read the transcripts, not only the totals. Anthropic's point is that the transcripts say why.

Its first uses

  1. Search-first routing (decision 0022, item 11's amendment): calls and answers, before and after.
  2. The uvm-requirements skill: with it, without it, and with only the server's instructions. This answers whether its routing list can shrink to a pointer.
  3. proposals_read, once proposal tasks exist: does it cut the five calls that "where does my proposal stand?" takes today?

What thirty tasks can show. Large changes: a tool no longer chosen, a call count that doubles, a fact that stops reaching the answer. Small differences fall inside run-to-run variance, as they do in the checklist ledger. The set grows the way the checklist keys grow, and each recorded run says how many tasks it ran.

What it costs. One run of thirty tasks is thirty agent sessions plus reading them, so each run is estimated and asked for first, under the owner's spending rule.

7. To rule

  • What a pass is, per tool (section 5): all required facts or a share of them for search, the top 10 for matching, every keyed deliverable for a checklist.
  • A keyed benchmark for documents_search, the one ranking tool without one.
  • An agent-level task set at all, given the two narrower refusals, and as a Low experiment first rather than design.md's Moderate one.
  • Who writes the tasks and their keys. The gate's keys were authored at /grading. Tasks with several keyed facts each may need the same review queue the checklist keys use.
  • Headless Claude Code as the harness, on the subscription, and which model it pins.
  • Whether a skill change needs a recorded run, as a drafter change already does.
